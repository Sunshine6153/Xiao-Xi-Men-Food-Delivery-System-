# 小西门管理端分步实现与验收方案

更新时间：2026-09-23  
状态：管理端基础版步骤 0–12 已全部验收；后续业务功能按第 5 节另行实施。

设计依据：[管理端基础设计](admin-design.md)。本轮目标是把**现有管理接口**做成可实际使用的管理端，同时为订单、用户、统计、销量排名等未来功能保留清楚的入口和“待接入”页面。未来功能的真实业务数据不纳入本轮“基础版完成”判定。

## 1. 执行规则

- 每个编号是一段独立、可在**一次对话**内实现和验证的工作。一次只做当前编号，不把后续页面顺手做到一半。
- 每段对话都要给出：改了什么、对接了哪些接口、正向和异常场景的验证结果、构建或测试结果、遗留问题。仅完成页面外观或仅编译成功，不算该步骤完成。若发现超出当前步骤范围的大缺陷，回到对应步骤修复，不把它塞进当前对话。
- 需要写后端的步骤在后端项目工作区执行。若数据库、Redis、测试账号或后端工作区不可用，先处理前置条件，不把模拟数据当作真实联调通过。
- 未接入页面可展示“待接入”和预期用途，但不提供看似可用的保存、处理或虚构指标。
- 管理员身份已采用商户账号的 `role` 字段，并由服务端登录响应、JWT 和 `/admin/auth/me` 校验。管理员业务页面仍须等服务端权限边界与对应接口验收后开放；前端本地角色不是权限依据。
- 验证用新增、删除和状态变更只针对测试数据；保留复测数据或记录恢复办法。

## 2. 开始前必须核实的事实

当前前端只有登录页，后端已实现商户登录、商户、分类、菜品接口。以下差异会直接影响步骤顺序：

1. 前端登录请求仍是 `/login`，后端实际地址是 `POST /admin/merchant/login`。
2. 前端按 `code === 1` 判断成功，但当前后端 `Result.success()` 返回 `code: 200`。其他业务错误也可能以 HTTP 200 携带业务错误码返回；请求层必须统一处理。
3. 步骤 6 已补齐登录响应、JWT 中的 `role` 与 `/admin/auth/me`。当前运行服务能区分 `ADMIN` 和 `MERCHANT`；细化到分类、商户等业务接口的权限边界仍按步骤 7 单独验收。
4. 菜品接口按 JWT 内商户 ID 限定数据，不能直接作为管理员跨商户菜品列表。
5. 商户资料更新存在明显代码问题：`MerchantDTO.setId` 未赋值，新增与更新密码处理不一致，数据库更新语句未写入 `location`。商户管理界面应在修复并复测后接入写操作。
6. 图片上传返回 `/images/...` 路径，前端开发代理与部署配置需要保证图片可显示；菜品缓存清理只供后端 Controller 内部调用，不对外提供 HTTP 接口。
7. 后端 `POST /admin/merchant/logout` 目前没有令牌失效逻辑。基础版“退出”以清除浏览器会话为验收标准；若要求立即撤销旧 JWT，需另立后端任务。

### 第 7 步权限边界实施与验收（2026-09-22）

原阻断：旧运行服务将 `/admin/merchant/**` 限为 `ADMIN`，但将其他 `/admin/**` 统一限为 `MERCHANT`；商家读分类为 `200`，管理员读分类为 `403`。后端源码已将分类读接口开放给两种已登录角色，分类写接口限 `ADMIN`，商户管理限 `ADMIN`，本店菜品限 `MERCHANT`；未知 `/admin/**` 路径默认拒绝，缓存清理方法不再对外暴露 HTTP 映射，并停止记录完整 JWT。

新增 `AdminPermissionBoundaryTest`，使用真实 Spring MVC、MySQL Mapper 和事务回滚测试数据，不启动订单定时任务，也不访问真实 Redis 缓存。两项测试均通过，覆盖匿名请求业务码 `401`；两种角色读分类业务码 `200`；商家对分类新增、编辑、启停、删除和商户管理写操作被拒绝；管理员分类写操作及商户新增通过；管理员访问商家菜品被拒绝；商家能读取及修改本人菜品，不能读取、修改、启停、删除其他商户菜品，伪造 `merchantId` 查询参数不能越权；未知管理路由默认拒绝；原缓存清理 URL 不再执行缓存操作。接口的 HTTP 响应仍为 `200`，实际权限结果在业务码中体现。`mvn -pl sky-server -am -DskipTests package` 通过。

经用户同意，已于 23:13 正常停止旧进程 `97721`，将最新构件启动为新进程 `99746`（端口 `8080`）。真实 HTTP 复验：两账号均能登录并经 `/admin/auth/me` 返回正确角色；匿名读分类业务码 `401`；商家、管理员读分类均为 `200`；商家调用商户分页业务码 `403`、管理员为 `200`；商家菜品分页为 `200`、管理员为 `403`；原缓存清理 URL 对商家返回 HTTP `400`、对管理员返回业务码 `403`，没有执行清理；不存在的管理路由返回 HTTP `404`。本轮运行服务探针仅执行登录与只读请求，未创建、修改或删除业务数据。**第 7 步验收通过。**

## 4. 基础版最终验收目标

全部成立才可标记“管理端基础版完成”：

1. 登录页保留现有校门照片和主要视觉；登录、刷新、过期、退出流程可用，前后端成功码和请求路径一致。
2. 商家与管理员看到各自允许的菜单和数据；服务端实际拒绝越权请求，不依赖前端隐藏按钮保护。
3. 商家完成本店菜品查询、筛选、详情、新增、编辑、图片上传、口味设置、上下架和删除；分类只用于筛选及表单选择。
4. 管理员完成全局分类与商户的增查改、启停和允许的删除；分类位于“菜品管理”二级菜单。跨商户菜品列表支持真实分页、筛选、详情和上下架。
5. 用户管理支持真实分页、搜索、详情和启禁用；订单、数据统计、销量排名及尚无接口的店铺编辑功能保留清晰的“待接入”页面，不展示虚构数字或可误触的操作。
6. 桌面和平板能完成基础版全部真实操作；手机能查看和执行基础操作；空数据、加载、错误和无权限状态可辨认。
7. 前端构建通过，后端相关测试通过；至少用两个商户账号和一个管理员账号完成实际接口联调，并保留验收记录。
