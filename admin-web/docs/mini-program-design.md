# 小西门校园美食配送系统

## 小程序客户端设计说明

版本：V1.0  
状态：设计已确认，准备进入前端实现  
更新时间：2026-09-19

## 1. 产品定位

小西门小程序不是传统的单商户外卖点餐工具，而是面向东北大学校园场景的：

> 小西门统一点餐 + 学生自主接单帮带 + 多商户协同制作 + 校园内配送

用户既可以购买餐品，也可以作为配送者接取其他学生的帮带订单。配送者不单独注册账号，普通用户账号同时具备购买和帮带能力。

小程序客户端弱化商户入口，以“菜品分类 → 菜品”为主要浏览路径；商户名称和摊位位置在菜品、购物车、订单详情中作为辅助信息展示。

## 2. 第一版范围

### 2.1 包含功能

- 微信登录
- 菜品分类浏览
- 菜品列表和详情
- 多商户统一购物车
- 手动填写帮带费
- 手动填写和管理配送地址
- 模拟支付
- 用户订单查看
- 全部待接订单浏览
- 学生自主接单
- 配送订单状态查看
- 用户确认收餐
- 商户营业状态对前端购买流程的影响展示

### 2.2 暂不包含

- 真实微信支付和资金结算
- 商户结算、提现、平台抽成
- 自动计算配送距离和配送费
- 强制派单、超时处罚、转单和自动重新派单
- 地图定位和路线规划
- 微信订阅消息通知
- 商户端和管理员端页面
- 后端代码和数据库修改

## 3. 信息架构

小程序采用四个底部 Tab：

```text
点餐
├── 菜品分类
├── 菜品列表
├── 菜品详情
├── 购物车
└── 确认订单

帮带
├── 待接订单列表
├── 待接订单详情
└── 接单

订单
├── 我买的

├── 用户信息
├── 地址管理
├── 我的订单

```

## 4. 页面设计

### 4.1 点餐首页

首页是默认入口，目标是让用户快速找到菜品并加入购物车。

页面区域：

1. 顶部品牌区域：小西门名称、校园美食副标题和当前整体提示。
2. 搜索框：支持按菜品名称搜索。
3. 分类导航：炒饭、面食、炸串、饮品、其他等，按接口返回的排序展示。
4. 菜品列表：展示图片、名称、描述、价格、所属商户、摊位位置和加购按钮。
5. 底部购物车栏：展示商品数量、商品合计和“去结算”按钮。

商户不是首页一级导航。菜品属于暂停营业商户时，显示“暂停售卖”并禁用加购；已下架菜品不展示或不可购买。

### 4.2 菜品详情

采用底部抽屉或半屏弹层，减少从菜单离开的操作成本。

展示内容：

- 菜品大图
- 菜品名称、描述和价格
- 所属商户及文字摊位位置
- 可选口味或规格
- 数量调整
- 加入购物车

相同菜品的不同口味组合应作为不同购物车行处理，避免覆盖用户选择。

### 4.3 购物车

购物车允许同时包含多个商户的菜品，但按商户分组展示：

```text
张记炒饭
  蛋炒饭 ×1       ¥8

王记炸串
  鸡柳 ×2         ¥12
  烤肠 ×1          ¥5

商品合计 ¥25                 去结算
```

支持增加数量、减少数量、删除单项、清空购物车。数量降为 0 时自动删除该项。

### 4.4 确认订单

页面顺序：

1. 配送地址
2. 配送要求
3. 帮带费
4. 订单备注
5. 菜品分组明细
6. 金额汇总
7. 确认支付

用户自行输入帮带费，不由系统计算。最终金额为：

```text
商品合计 + 帮带费 = 订单合计
```

第一版按钮文案使用“确认支付”，点击后调用模拟支付接口；支付成功后订单进入“待接单”。

### 4.5 帮带首页

展示所有处于“待接单”状态的订单，不做距离筛选和自动推荐。

每张订单卡片展示：

- 配送地址
- 帮带费
- 菜品概要
- 创建时间
- 订单金额或商品数量
- 查看详情

页面需要明确说明：配送者需要自行判断是否方便前往小西门取餐并完成配送。

### 4.6 待接订单详情

展示完整配送决策信息：

- 所有菜品
- 按商户分组的菜品明细
- 每个商户的摊位位置
- 配送地址
- 配送要求
- 帮带费
- 用户备注
- 接单按钮

接单成功后，订单从待接列表移除，并进入“我帮带的”。

### 4.7 订单

采用两个分段视图：

- 我买的
- 我帮带的

“我买的”可展示：待支付、待接单、制作中、待取餐、配送中、待确认收餐、已完成、已取消。

“我帮带的”可展示：制作中、待取餐、配送中、待确认收餐、已完成。

订单详情使用时间轴展示整体状态；在“制作中”阶段，额外展示各商户制作进度：

```text
张记炒饭   已完成
王记炸串   制作中
饮品摊     已完成
```

用户仅能在待支付、待接单状态取消订单；进入制作流程后不显示普通取消入口。

### 4.8 我的

包含用户基本信息、地址管理、我买的订单、我帮带的订单和设置入口。

默认允许用户先浏览菜品；执行加入购物车、提交订单、接单等需要身份的操作时，再触发微信登录。

### 4.9 地址管理

第一版使用手动文本地址，不接地图和位置选择器。

支持：

- 新增地址
- 编辑地址
- 删除地址
- 设置默认地址

地址示例：第五宿舍 301、第八宿舍楼下、某宿舍楼门口。

## 5. 订单状态表现

业务状态按需求文档展示为：

```text
待支付 → 待接单 → 制作中 → 待取餐 → 配送中 → 待确认收餐 → 已完成
    └──────────────────────────────────────────────→ 已取消
```

“制作中”由多个商户的制作进度共同决定。只有订单下所有商户的餐品完成制作后，整体订单才进入“待取餐”。

状态颜色建议：

- 待支付：橙色
- 待接单：蓝色
- 制作中：紫蓝色
- 待取餐：青绿色
- 配送中：品牌蓝
- 待确认收餐：橙色
- 已完成：绿色
- 已取消：灰色

### 6.2 组件风格

- 页面背景使用浅灰蓝色，内容使用白色卡片。
- 卡片圆角建议 12–16px。
- 使用轻阴影区分层级，不使用厚重边框。
- 主按钮使用品牌蓝，危险操作使用红色或橙色。
- 菜品图片要有足够视觉面积，价格和加购按钮保持高识别度。
- 商户名称和位置使用小型标签或次要信息，不抢占菜品主信息层级。
- 保持按钮、卡片、列表间距统一，优先保证移动端单手操作。

## 7. 前端实现边界

当前阶段只开发微信小程序客户端，不修改 Spring 后端、数据库和后端实体。

前端开发策略：

1. 使用本地 mock 数据完成页面和交互。
2. 将请求封装在独立 API 层，方法命名和路径按接口说明书预留。
3. 将订单状态、菜品状态、商户状态集中定义，避免页面散落魔法数字。
4. 微信登录先封装为登录服务，后端联调时再接入真实登录接口。
5. 模拟支付只改变前端订单状态或调用预留 API，不接真实资金渠道。
6. 等页面流程稳定后，再整理需要后端补充的字段、接口和状态校验清单。

## 8. 开发顺序

1. 小程序全局主题和底部 Tab 框架。
2. 点餐首页、分类切换、搜索和菜品卡片。
3. 菜品详情和购物车。
4. 确认订单和模拟支付。
5. 订单列表、订单详情和状态时间轴。
6. 帮带订单列表、详情和接单流程。
7. 我的、地址管理和微信登录占位流程。
8. 使用 mock 数据完成完整用户路径验收。
